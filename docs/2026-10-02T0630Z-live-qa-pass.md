`--primary` is never used as a text colour — `grep -c 'color:var(--primary)'`

This is a computed-token check. It is not a substitute for the rendered check,
because computed values cannot see a colour that is set in a place the tokens do
not describe. That is precisely what check 15 would have covered.

## Check 15 — reviewer leg: root cause is a quota/hosting constraint, not a bad key

The render leg is **healthy**. The reviewer leg is not. Six real PNGs were
captured this run at all three viewports and attached to
[STI-485](/STI/issues/STI-485):

`preview-stitch-ash-com-{1440x900,820x1180,390x844}.png` (home) and
`preview-stitch-ash-com-contact-{1440x900,820x1180,390x844}.png`.

The blocker recorded on this issue has changed shape. Earlier passes and the
issue title both record `401 invalid_api_key`. This run produced **three
different signatures**, in this order, and the last one is the informative one:

```
# 1. render leg, real PNG, text probe on the same key
HTTP 200  {"model":"fireworks/ember-1","content":"ok"}          <- text-only

# 2. same key, real PNG payload
HTTP 429  {"error":{"code":"model_cooldown",
  "message":"All credentials for model openai/gpt-5.6-sol are cooling down",
  "model":"openai/gpt-5.6-sol","reset_seconds":115}}

# 3. same key, same PNG, after honouring reset_seconds=115
HTTP 401  {"error":{"code":"invalid_api_key",
  "type":"authentication_error",
  "message":"[401]: You need to sign in to use this model."}}

# 4. same key, same PNG, later capture of /contact
HTTP 403  {"error":{"code":"insufficient_quota",
  "type":"permission_error",
  "message":"[403]: Error from provider (Console): OpenCode's free tier can only
   be used from within OpenCode"}}
```

The `403 insufficient_quota` message names the cause: the `auto/best-vision`
alias is routing image payloads onto an **OpenCode free-tier** provider, and that
tier refuses requests originating from outside OpenCode. This is a routing and
entitlement fault. The key is not the problem, and rotating
`OMNIROUTE_API_KEY` would be wasted work — the same key authenticated a text
call in this same run.

Two consequences worth acting on:

1. **A text-only health check reports this gateway green.** Item 1 above is
   HTTP 200 on the same key, same endpoint, seconds from the failing image
   calls, and it routed to `fireworks/ember-1` — a text model, not a vision
   model. Any monitor built on a text probe is blind to this entire failure.
   The probe must carry a real screenshot payload.
2. **The alias does not route to vision for image input.** The cooldown error
   names `openai/gpt-5.6-sol`, a text model, for an image payload. A name like
   `auto/best-vision` passing on a text probe is not evidence it is healthy for
   the payload that actually matters.

`auto/best-vision` is the default in the skill and the only model I attempted.
I did not go hunting for an alternative vision model to route around the
provider limit — that is an entitlement/credential decision, and per HARD RULE 5
it goes to the operator, not to me.
